# OpenINTJ 架构、代码与安全审查

- 日期：2026年10月26日
- 方式：基于当前工作区的静态审查
- 范围：主实现路径、设计文档、网络接口、桌面进程通信、工作区工具、持久化与任务编排
- 状态：未修改产品代码，也未运行测试

## 总体结论

当前设计的主要矛盾是：能力按“可信本机、单一用户”构建，却已通过网络接口、自动工具和恢复机制扩展到更高权限场景；认证、隔离、取消和数据一致性没有同步升级。

收益：

- 包边界清楚，输入输出校验广泛。
- 显式指定模型时失败即报错，不会静默退回模拟结果。
- 任务恢复默认不重放外部副作用。
- 原始输入可追溯。
- 进程通信契约、行为对齐、真实磁盘和桌面端到端测试较完整。

代价：三端装配、多套持久化、大量功能开关和历史设计承诺形成较高认知负担。当前更接近能力实验平台，距离可稳定运营的服务端和桌面产品还需要一轮收敛。

严重度包含触发前提。默认只监听本机、命令默认关闭，降低了即时风险，但不能消除启用对应能力后的设计缺陷。

## 最先处理的五件事

| 顺序 | 行动 | 原因 |
| --- | --- | --- |
| 1 | 重做命令执行接口 | 当前可执行文件白名单无法约束外壳语法 |
| 2 | 为服务端增加认证并隔离事件流 | 一旦对外暴露，会直接泄漏或修改本地长期状态 |
| 3 | 修复持久化写入队列 | 一次瞬时故障会变成之后所有写入静默丢失 |
| 4 | 让取消真正传到下层操作 | 超时后继续执行的副作用会破坏状态机可信度 |
| 5 | 抽出统一装配入口 | 阻止命令行、服务端和桌面端继续产生行为漂移 |

## 一、架构缺陷与取舍

| 优先级 | 问题 | 实际代价 | 证据 |
| --- | --- | --- | --- |
| 最高 | 服务端仍按本机单用户设计，却允许对外监听 | 监听地址可绑定到非本机，但接口没有认证，也没有租户或会话隔离 | `ts/apps/server/src/index.ts:9-10`；`ts/apps/server/src/routes.ts:28-363` |
| 最高 | 工作区沙箱只检查路径字符串 | 符号链接或目录联接可以把读写重定向到工作区根目录之外 | `ts/packages/planes/execution/src/workspace-tools.ts:53-65, 85-108` |
| 高 | 命令行、服务端、桌面端各自装配完整智能体 | 三端语义已经出现漂移，同一处行为修改需要同步三份代码 | `ts/apps/cli/src/agent.ts`；`ts/apps/server/src/agent.ts`；`ts/apps/desktop/src/main/agent.ts` |
| 高 | 持久记忆启动时全量装入内存 | 启动时间和内存占用随历史数据线性增长，缺少配额、分区和归档 | `ts/packages/planes/memory/src/persistent-store.ts:119-132` |
| 高 | 向量库与元数据库缺少一致性恢复 | 双写中断后可能留下孤立向量或缺失元数据，且无法自动对账 | `ts/packages/planes/memory/src/persistent-store.ts:224-238` |
| 中 | 独立可选开关过多 | 形成难以测试、支持和评估的行为组合矩阵 | `ts/apps/server/src/agent.ts:539-549` 等 |
| 中 | 设计文档与实际运行契约不一致 | 任务编排、桌面通信和模型运行时的完成声明、默认值与实现不完全一致 | RFC-003/004/005；`ts/apps/desktop/src/main/index.ts:144-157` |
| 中 | 桌面端存在两套持久化模型 | 一套仓储只被测试引用，生产实际使用工作台存储 | `desktop-persistence-repository.ts`；`workbench-store.ts` |

值得保留：

- 原始输入与执行输入分离，避免静默改写用户意图。
- 显式指定模型时失败即报错，避免生产环境误用模拟结果。
- 任务自动恢复默认取消，承认外部副作用无法保证只执行一次。
- 钝化记忆提案支持审批、撤销，并在落盘前脱敏。

应主动删除或降级：

- 未接入主路径的并发原语明确标为实验性。
- 合并工作台存储与只被测试引用的仓储实现。
- 用三到四个能力配置档替代大量独立开关。
- 给设计文档标注“已实现、部分实现、已被替代”，不再用历史文档代替当前契约。
- 删除运行时强制替换对象属性的依赖注入方式。

## 二、程序设计与可评审性

这里的“严重”指数据完整性或状态机可信度，不等同于远程安全严重度。

| 级别 | 发现 | 机制 | 证据 |
| --- | --- | --- | --- |
| 严重 | 异步写队列会永久失效 | 一次写入被拒绝后，后续排队写入都不再执行 | `persistent-store.ts:181-187, 222-238` |
| 严重 | 取消只停止等待，不停止实际工作 | 工具或工作节点超时后，文件、网络和命令副作用仍可能继续 | `tool-hub.ts:347-385`；`task-pool.ts:453-483` |
| 高 | 任务池工作节点启动后无人跟踪 | 调度错误可能变成未观察的失败，并使调度器永久等待 | `task-pool.ts:419-451, 631-639` |
| 高 | 服务端没有优雅关闭 | 收到终止信号时不排空请求，也不关闭智能体与数据库 | `server/src/index.ts:12-47` |
| 高 | 桌面端热重载存在生命周期竞态 | 旧实例关闭时，尚未结束的请求仍可能访问已关闭资源 | `desktop/main/index.ts:371-390` |
| 中 | 记忆平面的依赖在运行时被强制替换 | 存储和检索器不是构造时注入，内部重构后容易悄悄失效 | `server/agent.ts:463-470`；`desktop/agent.ts:518-524` |
| 中 | 外层循环超时不是硬截止时间 | 只在内层推理返回后检查，卡住的模型调用可以无限阻塞 | `core/loop/tao.ts:300-360` |
| 中 | 损坏的历史数据会让消息读取失败 | 先做原始解析，再做结构校验；非法内容会直接抛出异常 | `workbench-store.ts:93-107` |
| 中 | 任务队列不校验缺失依赖 | 关闭后仍处于等待状态的节点会让出队操作永久阻塞 | `task-queue.ts:63-75, 114-117, 187-197` |

建议建立 `@openintj/agent-runtime`：统一完成预检查、输入结构化、分类、规划、执行、结果约束和持久化。命令行、服务端和桌面端只提供模型、存储、工作区、产物和生命周期适配器。

- 智能体运行时：唯一执行流水线、截止时间、追踪、错误分类和收尾顺序。
- 能力适配器：持久化、工具、图片、工作区和界面行为显式注入。
- 传输外壳：命令行、网络接口和进程通信只负责协议映射、认证和生命周期。

## 三、安全风险与漏洞

默认只监听本机、桌面端为单用户、命令工具默认关闭，因此默认暴露面较小。下列高风险项主要在对外监听、启用命令、工作区含攻击者可控链接，或模型服务被攻陷时成立。

| 严重度 | 漏洞 | 影响与利用机制 | 位置 |
| --- | --- | --- | --- |
| 高（启用命令时） | 命令白名单可被外壳连接符绕过 | 只校验第一个词，随后把整条命令交给系统外壳；允许某个程序后仍可拼接其他命令 | `workspace-tools.ts:112-128` |
| 高（对外监听时） | 服务端接口没有认证和授权 | 可读取记忆、审计和用户画像，也可发起对话、审批和技能蒸馏 | `server/routes.ts:28-363` |
| 高（并发流式时） | 流式事件会跨请求泄漏 | 每个客户端订阅全局事件总线，没有按本次追踪标识过滤 | `server/routes.ts:53-99` |
| 高（工作区含链接时） | 符号链接或目录联接可逃出沙箱 | 路径检查只阻止上级目录，实际文件操作会跟随链接 | `workspace-tools.ts:53-108` |
| 中 | 模型返回的图片地址可触发服务端请求伪造 | 桌面主进程会跟随任意地址和重定向，没有私网地址限制 | `llm/hunyuan/image.ts:116-136` |
| 中 | 图片下载没有大小和类型硬限制 | 恶意响应可造成内存放大，非图片内容也会按图片保存 | `llm/hunyuan/image.ts:124-138` |
| 中（纵深防御） | 桌面渲染进程沙箱未启用 | 上下文隔离和内容安全策略已启用，但渲染进程漏洞的影响面仍然偏大 | `desktop/main/index.ts:252-260` |

修复原则：

- 命令与文件：使用无外壳的参数化进程启动；白名单匹配解析后的可执行文件；拒绝符号链接和重解析点，并校验已存在上级目录的真实路径。
- 网络接口与事件：非本机回环地址启动时必须配置认证；每次运行分配请求范围；流式响应只转发同一次追踪的事件，连接断开时中止任务。
- 网络下载：优先只接受内嵌图片数据；地址模式限定安全协议和域名，逐次校验重定向及域名解析结果，并限制响应长度和流式读取上限。
- 桌面端：启用渲染进程沙箱；所有进程通信注册器校验发送方来源；把产物生成快路径纳入相同的治理和审计边界。

## 四、优化路线

| 阶段 | 目标 | 交付物 |
| --- | --- | --- |
| 0–3 天 | 封住信任边界 | 改为无外壳的参数化命令；服务端认证并按追踪标识过滤事件；阻止链接逃逸；限制图片地址和大小 |
| 1 周 | 恢复可靠语义 | 写队列失败后可继续；统一取消信号；跟踪超时后的残留任务；服务端优雅关闭；容忍损坏的历史数据 |
| 2–4 周 | 收敛代码结构 | 抽出统一智能体运行时；记忆平面正式接收存储依赖；合并桌面端两套持久化实现 |
| 1–2 月 | 形成可运营能力 | 提供少量能力配置档、存储配额与惰性装载、任务池容量和成本指标，并回写设计文档 |

验收门槛：

1. 两个并发流式客户端互相收不到对方的任何事件。
2. 注入一次持久化写失败后，下一次写入仍能成功，并能观察到失败与恢复。
3. 超时返回后，不再发生文件写入、子进程继续存活或模型请求继续执行。
4. 目录联接和符号链接都不能越过工作区根目录。
5. 命令行、服务端和桌面端运行同一套契约测试，并明确记录允许存在的端侧差异。
