## 二、四条分支各自是什么

### `main`（主干）

一个**两代并存**的仓库：

- **Python 版（根级）**：`agent_loop.py` / `framework_core.py` / `context_engine.py` /
  `llm_client.py` / `main.py`，加四个 plane（`control_plane` / `execution_plane` /
  `governance_plane` / `memory_plane`），配 `Dockerfile` / `docker-compose.yml` /
  `nginx.conf` / `deploy.sh` / `requirements.txt`
- **TS 单体仓库（`ts/`）**：pnpm workspace + turbo + vitest + biome，
  `apps/cli`、`apps/desktop`（`@openintj/desktop` v0.3.1）、`packages/`（287 个文件）
- 附带：`docs/architecture`（18）、`docs/rfcs`（8）、`.github/workflows`、
  `scripts/python-parity`、`static/`、`openINTJ.zip`（0.1MB）

历史从 2026-04 起，最近一次提交是 2026-10-22 的
`chore(repo): drop git.woa.com remote and make GitHub the canonical host`。

### `UI-and-IDE`（本次目标）

推送前与 main 完全相同（空壳主题分支）。现在 = main + 我们的首版实现。

本次成果是**独立血统**：它来自 `delivery/` 的架构文档（G0~G6），
从未纳入过版本控制，与 `ts/apps/desktop` 没有共同祖先 ——
旧版有 `main/agent.ts` / `model-registry.ts` / `renderer/components/` / `shared/ipc-protocol.ts`，
而我们这套是 P-01/P-03/P-04 进程模型（`agent-host/` / `tool-host/` / `shared/approval.ts` / `shared/llm.ts`），
结构对不上，不是「改」出来的，是另起炉灶。

### `rfc-005-007-implementation`

与 main 逐字节相同，工作早已合回。名字是历史遗留。

> **注意**：它现在事实上是旧状态的完整快照。合并之后想找回旧代码，
> 它是唯一的活分支 —— 见第四节「合并前必做」。

### `archive-python-upload`

孤儿历史，只有 2 个提交（2026-04-20 的 `Initial commit` + `Add files via upload`），
内容仅 **9 个根级 Python 文件**。

> **注意**：它**不是**旧状态的完整快照 —— 只有建库那次上传的 9 个文件，
> 没有 `ts/`、没有 `docs/`、没有后来的任何东西。别指望靠它回滚。

## 四、合并前必做的三件事

### 1. 给旧状态打一个**说得清名字**的快照

目前旧状态的活分支只有 `rfc-005-007-implementation` —— 名字完全看不出它是快照。
半年后没人会想到去那里找 Python 版。

```bash
# 在 f4a3f69 上打 tag（推荐，tag 不会被人顺手删掉）
git tag legacy/pre-ts-rewrite f4a3f69e534e2418431a66e9db358e694f39f69f
git push origin legacy/pre-ts-rewrite
```

只靠 `rfc-005-007-implementation` 也行，但它是**可快进的分支**，
哪天有人把它同步到 main 就白留了。tag 更稳。

### 2. 决定 CI 怎么处理

- 要么合并前重写 `ci.yml` 指向新结构；
- 要么接受「合并即无 CI」，之后单独补。
  建议选前者：合并完主干没 CI，之后很容易忘。

### 3. 确认公开仓库里没有敏感内容

目标仓库是**公开的**。本次推送前已跑过 `node scripts/git/pre-push-scan.mjs`，
结论：只有 3 处命中，均为脱敏探针的**合成夹具**（已加 `// scan:ignore(理由)` 标记，
扫描结果里会列出豁免清单）。无真实凭据入库。

```bash
node scripts/git/pre-push-scan.mjs   # 退出码 0 = 可以推
```

> 提醒：公开仓库的密钥一旦进历史，轮换都不够，必须重写历史。
> 所以这个扫描应当在**每次推送前**跑，而不是等 CI 报警。

## 五、合并预案（三选一）

现状：`main` 自 `f4a3f69` 以来没有任何新提交，`UI-and-IDE` 只领先 1 个提交。
所以此刻合并是**纯净快进**，不会有冲突。

### 方案 A：快进合并（最简单）

```bash
git checkout main
git merge --ff-only UI-and-IDE
git push origin main
```

- 优点：历史线性、干净
- 缺点：主干历史里看不出「这里发生了一次代际替换」，像是自然演进

### 方案 B：留合并提交（推荐）

```bash
git checkout main
git merge --no-ff UI-and-IDE -m "merge: 主干切换为 TS 桌面端首版（G0~G6 落地）"
git push origin main
```

- 优点：主干上有一个明确的里程碑节点，将来翻历史一眼能看到「这里换了代」
- 缺点：多一个合并提交

### 方案 C：Squash 后合并

本次只有 1 个提交，squash 没有意义。若后续 `UI-and-IDE` 上又累积了多个提交再考虑。

## 六、建议顺序

1. `git tag legacy/pre-ts-rewrite f4a3f69 && git push origin legacy/pre-ts-rewrite`
2. 按新结构重写 `.github/workflows/ci.yml`（npm 而非 pnpm；`working-directory` 改到根）
3. 确认 `main` 无未合并的新提交（若有，先在 `UI-and-IDE` 上做一次 `--no-ff` 的反向合并解决冲突）
4. `git merge --no-ff UI-and-IDE` 并推送
5. 合并后删掉已成历史的 `rfc-005-007-implementation`（tag 已接管它的唯一价值）
