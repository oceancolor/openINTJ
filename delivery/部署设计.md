**必读前提（三条，决定本文档的写法）**：

1. **本系统 MVP 是桌面单机应用**（X1 已冻结，桌面壳层 = Electron，IC-01 已冻结）。因此模板中依赖「服务端集群」语义的条目（4 层 / 7 层负载均衡、HPA、跨 AZ 切换、集中式日志平台、堡垒机）在本系统内**无对应物**。本文档的处理纪律是：**逐条改写为其桌面端等价物并显式标注不适用及其理由，不留空、不虚构、不为填满模板而编造**。
2. **Q4 四项中已补齐两项**：**Region 确认为中国境内使用**（具体 Region 值仍待定，暂按「待定 · 假定 ap-guangzhou」标注）、**预算上限 = 人民币 1000 元 / 月**（落盘为 SB-05 熔断阈值，**不用于反推单价**）；**仍缺云账号与实例规格两项**。U-05（腾讯云 CVM 是否透传 `/dev/kvm`）未核实，但隔离原语形态**已由 IC-14 定为容器**。因此云端三项的容量、并发、TTL、成本模型**仍只出接口与估算方法，不出任何数值**，并在每一处显式标注「待 Q4 补齐」。本文档**不自行假设任何配额、规格或单价数字**。
3. **云端资源归属用户**：IC-03 冻结为自建、IC-04 冻结云厂商为腾讯云，但云端资源创建在**用户自有腾讯云账号**内，本系统只提供接口与部署脚本，**不代持账号、不代收费用、不托管账单**。这一条是 §2 资源清单与 §8 成本模型的前提。

## 1. 引言

### 1.1 适用范围与部署形态

#### 1.1.1 部署形态总览

| 维度 | 本系统的取值 |
| --- | --- |
| 系统范围 | ① openINTJ Agent Console 客户端本体（Windows / macOS 安装包）；② 其依赖的**桌面分发与更新通道**；③ 用户在**自有腾讯云账号**内自建的**云端供给面**（云端工作区 / 云端沙箱 / 云端预览）；④ 支撑上述三者的 CI 与制品链路 |
| 部署形态 | **混合形态，且云端部分不由本系统托管**：客户端本体为「私有化到用户机器」的本地部署（100% 落在用户终端）；云端部分为「用户自有账号内的自建」（IC-03 / IC-04）。二者之间无本系统运维的常驻服务端 |
| 公有云依赖面 | 客户端运行时**不依赖**本系统运营的任何公网服务端；对外只有「客户端主动出网」与「分发通道的下载」两个方向 |
| 数据驻留 | 用户代码、事件流、审计、凭据默认全部留在本机（C8）；云端侧为 ephemeral 一次性副本，会话结束即销毁（IC-09 方案 A） |
| 不受本文档部署范围约束的三项 | ① 用户机器操作系统本身（OS 稳定性与电力归用户，见 §3.3.1）；② 用户自有的 LLM 供应商（E-01 / E-02，由用户自行登记端点与凭据）；③ 第三方 MCP Server（E-03，其部署形态由 MCP server 提供方自行决定） |

&gt; **形态纪律**：本系统**不是** Web 系统（O5），**不是** 多租户 SaaS（O3），**不是** 云端主副本架构（IC-09 方案 A）。凡本文档中出现「集群」「副本伸缩」「集中式看板」字样处，均为其桌面端等价物的改写，不得据此推断存在服务端集群。

## 2. 环境与资源清单

### 2.1 环境矩阵

&gt; **桌面端适配说明**：本系统无服务端集群，四环境的隔离载体是**发布通道 + 数据目录 + 签名身份 + 遥测上报开关**四项，而非集群。本表在《系统设计》§5.1 已锁定的「环境数量 4 个 + 隔离方式」基础上，补齐部署侧所需的载体细节。

| 环境 | 用途 | 集群隔离（本系统的等价载体） | 数据 | 网络访问 | 签名与公证 | 更新通道 | 数据目录 | 遥测上报 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| dev | 开发自测（本地构建，未签名未公证） | 与 int 共用开发者本机；**独立数据目录** | 模拟数据 / 本地自造工作区 | 内网（开发者网络） | 无（未签名，允许远程调试与非签名启动） | dev 通道 | `{dataDir}/dev` | 强制关闭（不可开启） |
| int | 联调（内部构建，已签名但未发布） | 独立构建产物目录 + **独立数据目录** | 模拟数据（与 dev 隔离） | 内网 | 签名但不公证（macOS 侧可用本地签名绕过 Gatekeeper 的临时形态） | int 通道 | `{dataDir}/int` | 强制关闭（不可开启） |
| uat | 预发 / 内测（内部发布通道，灰度用户可订阅） | **独立发布通道 + 独立数据目录** | 仿生产（完整事件与审计留存） | 内网 + 白名单 | 签名 + 公证齐全 | uat 内测通道 | `{dataDir}/uat` | 默认关闭（可开启用于内测采集） |
| prod | 生产（正式发布通道） | **独立发布通道** | 真实数据 | 公网 / 内网（客户端所在网络） | 签名 + 公证齐全 | prod 正式通道 | `{dataDir}`（默认路径） | 默认关闭（用户显式开启才上报） |

**环境切换的三个硬约束**：

1. **数据目录隔离是强制的**：dev / int / uat 三环境必须与 prod 使用不同的数据目录，由 L3 环境变量 `OPENINTJ_DATA_DIR` 传入；未传入时使用平台默认路径。跨环境共用数据目录会导致事件库与审计库被污染，属于发版红线。
2. **通道不可混用**：更新通道标识在构建期写入产物（L1 层常量），运行时只读；禁止运行时修改通道，防止 dev 包意外接收 prod 更新。
3. **同一数据目录仅允许一个客户端实例**（承接《系统设计》§7.2.1 会话管理）：第二实例启动时聚焦已有窗口，不新起一套进程树与 SQLite 连接。

#### 2.1.1 云端侧环境划分

云端侧环境在 Q4 补齐前**只划分到接口层，不做物理环境切分**，原因：云端资源创建在用户自有账号内，创建何种环境由用户决定，本系统无权也无需代建 dev / int / uat / prod 四套云端环境。

| 云端项 | MVP 阶段取值 | Q4 补齐后的待定内容 |
| --- | --- | --- |
| 云端环境数量 | **单环境**（用户自有账号内的一个 Region，Region 待定 · 假定 ap-guangzhou） | 是否划分 dev / prod 两套云端环境，由用户在 Q4 补齐后自行决定 |
| 环境隔离载体 | 用户自有账号边界 + CAM 子账号 | 子账号与角色数量（《系统设计》§3.1.3 C-08 给出 ≤ 10 个的容量口径） |
| 本系统提供的东西 | `SandboxProvider` / `PreviewProvider` 接口 + 自建部署脚本 + 回收与夜巡脚本 | 规格、网段、配额阈值、并发上限、TTL 上限 |

| 用户自有腾讯云账号（承载 R-C-005 / R-C-006 / R-S-005 / R-S-006 / R-N-002 ~ R-N-006 / R-M-004 ~ R-M-006 / R-Sec-004 / R-Sec-005） | **用户本人** | 待人工确认（Q4 阻塞：账号 / Region / 配额 / 预算四项未补齐，无法评估余量） | **账号级隔离**：全部云端资源创建在用户自有账号内，与项目自有账号（分发侧）无任何共享；本系统只持有用户显式登记的临时凭据引用 |
| 本机 OS 凭据保险箱（R-Sec-003） | 用户 OS | 不适用（OS 原生能力） | 进程级：`safeStorage` 仅在 P-01 主进程内解密一次，明文不跨进程广播 |

&gt; **复用清单中「原业务方 = 用户本人」这一行的含义**：这是本系统区别于常规部署设计的最大不同——云端资源的**所有者、付费者与运维责任方都是用户**，本系统只提供接口与脚本。因此云端侧不存在「本系统代持的云资源」，也就不存在常规意义上的「云端余量评估」与「云端容量规划」，§8 据此只出接口与估算方法。

**拓扑读法（三条关键结论）**：

1. **桌面端无入站**：`HOSTPC` 与 `EXTDEP` 之间的连线全部是**出网方向**（箭头从 P-xx 指向外部），没有任何一条指向 P-xx 的入站连线。外部世界无法主动连入用户机器。
2. **云端侧只有一个入口方向**：`U2 → CAM` 是唯一的**管理面**入口（用户在自己的腾讯云控制台操作），`U1 → CVM` 与 `U1 → PB` 是**数据面**的投射与取回，二者分离。
3. **分发链路与云端链路在账号层面物理分离**：`DIST` 属项目自有账号，`CLOUD` 属用户自有账号，二者之间无连线——这意味着**分发链路的故障不会影响云端三项，反之亦然**。

#### 3.1.3 进程模型 P-01 ~ P-07 的部署落地

&gt; **本小节是《系统设计》§3.1.1.1 进程模型在部署侧的施工落点**：上游定义的是「进程是什么、为什么这么切」，本节定义的是「每个进程在部署上怎么被拉起、怎么被监护、怎么被限制、崩了怎么办」。

| 进程 | 部署侧的拉起方式 | 常驻策略 | 资源限额 | 崩溃处置（部署侧动作） | 部署侧硬约束 |
| --- | --- | --- | --- | --- | --- |
| P-01 主进程 | 用户双击图标 / 命令行启动时由 OS 拉起 | 常驻 | 由 Electron 默认 + 渲染进程 `--js-flags` 老生代上限 | 需用户重启客户端；部署侧提供崩溃上报（默认关闭）与 §6.2 的 RB-02 | 唯一持有 `safeStorage` 访问权 |
| P-02 渲染进程 | P-01 创建 `BrowserWindow` 时创建 | 常驻 | `contextIsolation = true`、`nodeIntegration = false`、CSP 锁定 | P-01 重建窗口，UI 从事件流重建状态 | 无任何 Node 能力；未经 `preload` 登记的通道一律拒绝 |
| P-03 `agent-host` | **首个任务启动时**由 P-01 以 `utilityProcess` 拉起（懒加载） | 按需（首任务后常驻） | 内存软限额（超限触发上下文压缩，不 OOM） | P-01 监护重启 + 从最近检查点续跑 | 不得在冷启动路径上初始化（N1） |
| P-04 `tool-host` | 首次工具调用前由 P-01 以 `utilityProcess` 拉起（懒加载） | 按需 | 内存软限额 | P-01 监护重启；在飞工具调用按幂等键重试 | 承载 `node-pty` 与 `better-sqlite3`，必须 ABI 重建 |
| P-05 VSCodium | 首次打开 IDE 面板时才解压并启动（懒加载） | 按需 | 随 Electron 子进程默认 | 禁用面板（BD-11），终端与执行流不受影响 | 冷启动路径**不得**触碰 `vendor/vscodium` 资源 |
| P-06 MCP Server 子进程 | 由 P-04 以 stdio 拉起，生命周期由 MCP 网关管理 | 按需 | 随系统默认 | 摘除并告警（BD-09），其余 server 正常 | stdio 形态不出网；远程端点须 https 且逐次授权 |
| P-07 预览子进程 | 用户在预览面板点击启动时由 P-04 拉起 | 按需 | 随系统默认 | 换端口重试 1 次（BD-07）；夜巡回收 | **只绑定 `127.0.0.1`**，禁止 `0.0.0.0` |

**进程间通信的部署侧硬约束（三条，违者视为重大部署缺陷）**：

1. **一律 `MessagePort` 结构化克隆，禁止本地 HTTP 端口**。这是 C8「代码不出本机」在进程级的兑现——本地 HTTP 端口意味着本机任何其他进程都可连入该端口。
2. **单帧载荷上限 8MB，超限分片**；渲染侧事件流推送合并窗口 50ms，保障呈现 P95 ≤ 500ms。
3. **禁止传递函数与原生句柄**：结构化克隆不支持，且会破坏进程隔离边界。

### 3.3 高可用与故障容错

#### 3.3.1 故障域划分

&gt; **模板要求是四层故障域**。本系统的四层为「进程 / 本机 / 云端实例 / 云端 Region」，与模板的「Pod / Node / AZ / Region」逐层对应，但每一层的物理含义按桌面端与 ephemeral 云端改写。

| 故障域 | 影响范围 | 容错机制 | 预期 RTO |
| --- | --- | --- | --- |
| 第一层：单进程（P-02 / P-03 / P-04 / P-05 / P-06 / P-07） | 该进程承载的单一职能不可用 | P-01 监护重启 + 从最近检查点续跑（QS-01）；P-02 崩溃则重建窗口并从事件流重建 UI 状态；P-06 崩溃则摘除该 server | ≤ 10 秒（P-03 / P-04）；&lt; 5 秒（P-02）；&lt; 1 秒（P-05 面板置灰） |
| 第二层：主进程（P-01） | 整个客户端不可用 | 需用户重启客户端；重启后从检查点续跑 | ≤ 30 秒（含用户操作时间） |
| 第三层：本机磁盘 / 整机 | 全部本地数据与在飞任务 | 依赖 §6.1.2 的全量快照还原与 §6.2 的 RB-03；**用户自行重装客户端** | ≤ 30 分钟 |
| 第四层：云端单实例 | 该沙箱会话失败 | **不做实例修复**：按 IC-09 方案 A 重新投射一次；孤儿实例由夜巡强制回收（SB-03） | 待 Q4 补齐后定义（不出数值） |
| 第四层：云端单 Region | 全部云端能力不可用 | 云端入口置灰，本地链路照常（BD-12）；本地主副本不受任何影响 | 待 Q4 补齐后定义（不出数值） |

| 可用性来源 | 范围 | 责任方 |
| --- | --- | --- |
| 用户机器与操作系统 | 电力、磁盘、OS 稳定性、系统资源 | **用户**（本系统不接管、不配置用户防火墙） |

#### 3.3.2 负载均衡

&gt; **桌面端：4 层与 7 层负载均衡均不适用**。理由：桌面端只有一个客户端实例、无多副本、无入站流量，没有任何需要分发到的后端。

| 层次 | 本系统的取值 | 等价物 |
| --- | --- | --- |
| 4 层负载均衡 | **不适用**（无多副本、无入站） | 桌面端等价物：**并行度调度器**（把任务分派到 1 ~ 8 个并行子 Agent 的逻辑单元，IC-12 上限 8）。云端侧：CLB 是否引入取决于 preview 形态，**规格待 Q4 补齐后定义** |
| 7 层负载均衡 | **不适用**（无 HTTP 服务端、无 Ingress） | 桌面端等价物：**IPC 通道白名单 + `preload` 上下文隔离**（把能力调用收敛到登记过的通道，等价于 7 层的路由与准入）。云端侧：反代（R-M-005）承担 7 层路由，仅用于 ephemeral preview |
| 会话保持 | 桌面端：**不适用**（无多副本） | 等价机制为「检查点续跑」：进程崩溃后从最近检查点恢复，等价于会话不中断 |
| 云端侧健康检查 | 待 Q4 补齐后定义（路径 / 频率 / 失败阈值三参数均为空） | 见 §3.3.3 |

#### 3.3.3 健康检查配置

**桌面端：进程级心跳（替代传统负载均衡健康检查）**

| 维度 | 取值 |
| --- | --- |
| 类型 | 进程级心跳，**无 4 层 / 7 层健康检查** |
| 上报方式 | P-03 / P-04 每 **5 秒**向 P-01 上报一次心跳，携带内存占用、当前任务数与最近错误计数 |
| 失败判定 | 连续 **3 次**（即 15 秒）未上报视为不健康 |
| 恢复阈值 | 连续 **2 次**成功上报视为恢复健康 |
| 不健康处置 | P-01 终止并重启该 Utility Process；任务从最近检查点续跑 |
| Liveness 等价物 | 进程心跳——仅判进程存活，不做业务语义判断 |
| Readiness 等价物 | 依赖就绪判定：SQLite 可写 + 凭据可用 + 工作区可访问；未就绪则不接受新任务（**不杀进程**），并在 UI 明示未就绪原因 |

**云端侧：健康检查三参数留空**

| 参数 | 取值 | 补齐条件 |
| --- | --- | --- |
| 健康检查路径 | 待定（Q4 阻塞） | Q4 补齐后按 R-M-005 的选型填入 |
| 检查频率 | 待定（Q4 阻塞） | 同上 |
| 失败阈值 / 连续成功阈值 | 待定（Q4 阻塞） | 同上 |

&gt; **为何云端健康检查也必须留空**：健康检查的三参数直接决定预热池（SB-02）的容量与实例回收（SB-03）的判定节奏，而池容量属 Q4 阻塞的配额范畴。在配额未定前填任何数字都会构成 C4 禁止的数值型承诺，因此本文档一律留空并标注补齐条件。

#### 3.3.4 弹性伸缩配置

**桌面端：并行度自适应（替代副本伸缩）**

| 维度 | 取值 |
| --- | --- |
| 触发指标 | 本机 CPU 使用率、可用内存、事件写入延迟 |
| 提升并行度 | CPU &lt; 60% 且可用内存 &gt; 2GB 持续 60 秒 → 并行度向用户配置值回升 |

| 冷却时间 | 提升 60 秒 / 降低 30 秒 |
| 生效耗时 | &lt; 1 秒（仅调度参数变更，不涉及进程创建） |

**云端侧：预热池伸缩（三项参数留空）**

| 参数 | 取值 | 补齐条件 |
| --- | --- | --- |
| 预热池容量水位 | 待定（Q4 阻塞） | 需 Q4 的配额与预算两项输入 |
| 扩缩容阈值 | 待定（Q4 阻塞） | 同上 |

**预览会话的回收（不依赖 Q4 即可落地的一条）**

| 对象 | 回收触发 | 回收动作 |
| --- | --- | --- |
| 本地预览会话（P-07） | 用户关闭预览面板 / 客户端退出 | 终止子进程并释放端口 |

#### 3.3.5 容灾切换配置

| 维度 | 取值 |
| --- | --- |
| 桌面端容灾级别 | **单机单副本**（X1 桌面客户端的必然推论，无集中切换动作） |
| 桌面端故障切换 | 无自动切换；等价物为「进程监护重启 + 检查点续跑」与「全量快照还原」 |
| 桌面端 RTO | 进程级 ≤ 10 秒；整机级 ≤ 30 分钟（与《系统设计》§4.3.2 同源） |
| 桌面端 RPO | 进程崩溃 ≤ 200 毫秒；整机 / 磁盘故障 ≤ 24 小时 |
| 云端容灾级别 | **单 Region**（Region 待定 · 假定 ap-guangzhou）；**不做跨 Region 灾备** |
| 云端故障切换 | **不做实例级切换**：IC-09 方案 A 下失败策略是「重新投射一次」，而非「修复实例」或「切到备用实例」 |
| 云端跨 Region 数据同步策略 | **不适用**：云端无持久状态需要保护，唯一事实来源在本机主副本（C8） |
| 恢复演练 | 频率 **每季度 1 次**；负责人 `@平台与安全组`；内容含全量快照还原、事件哈希链校验、从检查点续跑三项 |

**不做跨 Region 灾备的三条理由（正面说明，非回避）**：

1. IC-09 方案 A 下云端不存在需要保护的持久副本，跨 Region 灾备的保护对象不存在；
2. 云端资源创建在用户自有账号内，跨 Region 意味着用户需在两个 Region 各备一套配额，本系统无权也无必要替用户做这个决定；
3. 云端能力不可用时，本地主链路（C8）不受任何影响，业务连续性由本地链路保障，不依赖云端灾备。

### 4.2 流水线（CI / CD）

&gt; 流水线共 **8 阶段**，与模板一致。阶段 1 ~ 4 在每次推送时执行，阶段 5 ~ 8 按分支与人工审批推进。凡涉及 macOS 的阶段必须在 R-C-003（macOS 执行器）上运行。

| 阶段 | 触发条件 | 关键动作 | 失败处理 |
| --- | --- | --- | --- |
| 1. 构建 | 推送到任意分支 / PR | 拉代码 → lockfile 校验 → TypeScript 编译 → 单元测试 → 三平台（`win` / `mac` / `linux`）并行构建 → **`@electron/rebuild` 重建 `node-pty` 与 `better-sqlite3` 并断言 `process.versions.modules` 一致** | 阻断后续阶段；ABI 不一致直接 fail-fast（不降级为警告） |
| 2. 代码扫描 | 阶段 1 通过后 | 静态扫描（ESLint + TypeScript `strict` 全开）+ 复杂度与规范检查 | 严重问题数不为 0 则阻断；中危需评审 |
| 3. 安全扫描 | 阶段 1 通过后（与阶段 2 并行） | SCA（npm 依赖漏洞）+ SAST（代码漏洞）+ **二进制与内嵌组件扫描（Electron / VSCodium / node-pty）** | 高危漏洞 0 容忍，直接阻断；中危需评审 |
| 4. 集成测试 | PR 合入 `develop` | 集成测试 + IPC 契约测试 + **三平台冒烟（pty 可 spawn、SQLite 可写、VSCodium 子进程可启动）** | 阻断后续阶段 |
| 5. 制品打包构建 | 阶段 1 ~ 4 全绿 | 产出 NSIS / MSI / dmg / pkg / AppImage / deb → **Windows Authenticode 签名 → macOS Developer ID 签名 + notarize + stapling** → 生成 blockmap 差分元数据 → 推送到制品存储（R-S-004）并打 Tag → **计算并记录冷启动与常驻内存基线** | 失败重试 1 次；签名或公证失败直接阻断（不产出无签名制品） |
| 6. 部署集成环境 | 阶段 5 完成（自动，仅 `develop` 分支） | 发布到 **int 通道**；更新元数据端点写入版本清单 | 保留上一版本清单，不覆盖；失败则停止发布 |
| 7. 部署测试环境 | 手动触发（在 `release/*` 分支上） | 发布到 **uat 内测通道** → 内测冒烟（含冷启动 P95 与空闲内存基线复核）→ **四项发版必测**（硬闸门 / 越权拦截 / 凭据不明文 / 审计留痕 100%，见 §4.5.4） | 保留上一版本；四项必测任一不通过则整体阻断 |
| 8. 部署生产环境 | **人工审批**（至少 1 名 Owner） | 发布到 **prod 正式通道** → 灰度放量（见 §4.5.3） | 按 §6.1 回滚机制实施回滚 |

**流水线的三条桌面端特有约束**：

1. **阶段 1 的三平台并行是硬要求**：`node-pty` 与 `better-sqlite3` 的 ABI 在不同平台不同，任一平台构建失败即整体失败，不允许「Windows 能跑就行」。
2. **阶段 5 的 macOS 公证不可省略**：未经公证的 macOS 包会被 Gatekeeper 拦截，等于用户无法安装。
3. **阶段 4 的三平台冒烟项固定为三项**（pty 可 spawn / SQLite 可写 / VSCodium 子进程可启动），这三项分别对应 R-07 的原生模块风险、C-01 的持久化风险与 IC-02 的内嵌 IDE 风险。

#### 4.4.1 IC-08 三档审批的部署侧默认下发策略

&gt; 本小节是 IC-08（三档审批，默认标准）在部署侧的落地细则。

| 配置项 | 键 | 出厂默认值 | 值域 | 部署侧策略 |
| --- | --- | --- | --- | --- |
| 审批档位 | `policy.tier` | **`standard`**（IC-08 默认档 = 标准） | `relaxed` / `standard` / `strict` | 首次启动时写入 L2；用户可在「设置与凭据中心 → 权限与审批」区自行切换，**不做强制引导**；版本升级保留用户值 |
| 命令风险分级表 | `policy.riskRules` | 内置四类（L0 只读 / L1 工作区内写入 / L2 工作区外写入 / L3 危险命令） | JSON 数组 | **R4 内置规则恒置顶且不可删除**；用户可增删改其余规则；写操作带版本号乐观锁，并发冲突时后写失败并提示 |
| 档位到双轴的映射 | 代码内常量（L1） | 宽松 / 标准 / 严格 → `ApprovalPolicy` × `SandboxMode` 的映射表 | 固定 | 不暴露为用户配置项（避免用户配出不一致组合） |

| 审批并发保护 | 代码内常量（L1） | 只读与工作区内写入**不进入串行审批队列** | 固定 | 保障 IC-12 并行上限 8 不被审批队列退化为串行执行 |

**档位配置的备份与迁移语义**：

1. 档位与风险分级表存在 L2（SQLite 内），因此**自动随全量快照备份**，还原快照即还原用户的审批配置；
2. 跨版本升级时，若新版新增了内置规则，**追加而不覆盖**用户已有规则；
3. 用户导出诊断包时，档位与规则随配置一并导出，但**凭据类字段整列剔除**。

### 4.5 发布策略

#### 4.5.1 发布方式

&gt; 全系统统一采用「**发布通道 + 差分更新 + 灰度放量**」的桌面端发布方式。模板所列四种方式在本系统的对应关系如下。

| 模块 | 发布方式 | 说明 |
| --- | --- | --- |
| 客户端本体（桌面端全部模块） | **灰度放量（按通道与用户分批）+ 差分更新** | 无固定服务端，无法做服务端侧的蓝绿；桌面端的等价灰度是「内测通道 → 正式通道分批发放更新清单」 |
| 内嵌 VSCodium（P-05 二进制） | **随客户端整体发布，不做独立热更新** | 版本锁定策略见 U-06；随安装包整体替换，避免 IDE 与壳层版本错配 |
| 云端沙箱镜像（R-M-006） | **镜像版本滚动 + 双版本并存** | 新旧镜像同时可用，投射时可指定镜像版本；规格与版本数**待 Q4 补齐后定义** |
| 云端预览（ephemeral） | **不适用（无版本发布概念）** | 每个预览会话是新建的，不存在「升级已有预览」 |
| 蓝绿发布 | **不适用** | 桌面端无两套并存的服务端实例可供切换 |
| 金丝雀发布 | 部分适用 | 桌面端的等价形态是内测通道（uat）小范围用户先行，与灰度放量合并实现 |
| 特性开关（Feature Flag） | 适用（L2 配置层） | 云端三项在 Q4 补齐前可通过 L2 开关控制可见性；**默认档位与审批配置不受开关影响** |

#### 4.5.2 发布标准流程

**一、首次发布标准流程（含资源初始化）**

1. 创建制品存储（R-S-004）与分发端点（R-N-001），Region 待定 · 假定 ap-guangzhou；
2. 创建四条发布通道的更新元数据路径（dev / int / uat / prod）；
3. 采购并配置签名与公证凭据（R-Sec-001 / R-Sec-002），私钥注入 CI 密钥库；
4. 配置 CI 三平台执行器（R-C-002 / R-C-003 / R-C-004）；
5. 在流水线阶段 5 产出首个签名 + 公证齐全的正式版制品；
6. 执行阶段 7 的**四项发版必测**；
7. 人工审批后发布到 prod 正式通道；
8. 首次发布**不做灰度**，直接全量（无存量用户）。

**二、常规迭代发布流程**

1. `feature/*` → `develop`：CI 阶段 1 ~ 6 全绿，自动发布到 int 通道；
2. 冻结期：从 `develop` 切 `release/{version}`，只收缺陷修复；
3. 阶段 5 产出签名 + 公证齐全的候选制品；
4. 阶段 7 执行四项发版必测 + 冷启动与内存基线复核；
5. 人工审批 → 发布到 uat 内测通道 → 观察一个观测窗口（见 §4.5.3）；
6. 观测窗口无异常 → 灰度放量到 prod 正式通道；
7. 灰度批次全部通过 → 全量发放更新清单。

**三、资源变更流程**

| 变更类型 | 流程 |
| --- | --- |
| 云端资源变更（规格 / 网段 / 配额） | **Q4 补齐前不发生**（无账号可变更）；补齐后由用户在自有账号内执行，本系统只更新部署脚本 |
| 分发链路变更（CDN / 桶 / Region） | 变更前在 int 通道验证下载链路 → 灰度切流 → 观察下载成功率 → 全量 |
| 签名证书轮换（R-Sec-001 / R-Sec-002） | 新旧证书并存期 ≥ 一个版本周期 → 新证书先行签名 → 旧证书仍可验证存量包 → 到期后下线 |
| 内嵌 VSCodium 版本升级 | 在 int / uat 通道各验证一次 IDE 面板可用性 → 随下一个正式版整体发布 |

#### 4.5.3 灰度路径与观测窗口

&gt; 桌面端无服务端，灰度载体是**更新清单的分批发放**：更新元数据端点（META）按批次逐步把新版本清单放给客户端。

| 批次 | 放量范围 | 观测时长 | 放量条件 |
| --- | --- | --- | --- |
| 批次 0：内测通道 | uat 通道的内测订阅用户 | 不少于 1 个完整工作日 | 四项发版必测通过 + 冷启动与内存基线达标 |
| 批次 1：正式通道 5% | prod 通道随机 5% 客户端 | 24 小时 | 批次 0 无 P0 / P1 告警 |
| 批次 2：正式通道 25% | prod 通道随机 25% 客户端 | 24 小时 | 批次 1 无 P0 / P1 告警，且崩溃率不高于上一版本 |
| 批次 3：正式通道 100% | prod 通道全部客户端 | 72 小时持续观测 | 批次 2 无 P0 / P1 告警 |
| 回滚判定点 | 任一批次内 | 实时 | 触发 §6.1.1 任一条件即停止放量并回滚清单 |

**每个批次的四项观测指标（全部来自内置可观测面板）**：

1. 客户端启动成功率（承接 AL-02：主进程连续 3 次启动失败为 P0）；
2. 崩溃率（与上一版本对比，**不退化**为放行条件）；
3. 冷启动到可交互 P95（目标 ≤ 3 秒）；
4. 空闲内存占用（目标 ≤ 300MB）。

&gt; **灰度粒度纪律**：桌面端灰度只能做到「清单发放比例」，无法按用户属性精准圈选，这是桌面形态的固有限制，本文档如实说明，不虚构用户分群能力。

## 5. 监控告警接入

### 5.1 监控架构与数据流

&gt; **桌面端适配前提**：**无服务端日志平台**。所有可观测数据默认留在本机（C8）。Metrics 存进程内 + SQLite 物化统计；Logs 写本地结构化 JSONL；Traces 在进程内与跨进程用同一 `traceId` 串联并导出为本地 OTLP JSON 文件。**云端上报与集中式看板不在 MVP 范围**。

```text
P-01 ~ P-07 进程 ──┬─► Metrics ──► 本地指标库 (R-O-001) ─────────────┐
                   ├─► Logs    ──► 本地 JSONL 文件 (R-O-002)         │
                   ├─► Traces  ──► 本地 OTLP JSON 导出 (R-O-003)     │
                   └─► 审计    ──► t_audit_event 哈希链 (R-S-008)    │
                                                                    ▼
                                                    内置可观测面板 (R-O-004)
                                                                    │
                                                                    ▼
                                                   内置告警中心 (R-O-005)
                                                                    │
                                        ┌───────────────────────────┼───────────────────────────┐
                                        ▼                           ▼                           ▼
                               系统通知 (OS 原生)           Webhook 外送 (R-O-008)     崩溃上报 (R-O-006，默认关闭)
```

**数据流的三条纪律**：

1. **默认不出本机**：Metrics / Logs / Traces / 审计四路数据默认全部留在本机，只有用户显式订阅（Webhook）或显式开启（崩溃上报）时才外送。
2. **外送内容强制脱敏**：Webhook 外送不含 L4 凭据、不含事件流正文；崩溃上报不含用户代码、不含凭据。
3. **云端侧可观测不强制**：R-O-007（CLS / 云监控）由用户在自有账号内按需开启，本系统不代运维用户账号。

| **AL-18（G5 新增）** | P3 | 安装包体积超出 150MB 或首屏 JS 体积超出 2MB | R-S-004 | `@研发团队-客户端组` | `docs/runbook/AL-18-体积超标.md` |

**告警编号到 Runbook 的对应纪律**：AL-01 ~ AL-18 共 18 条，每条均有 Owner 与 Runbook 路径，编号与 §6.2.1 Runbook 索引一一对应。

## 6. 应急与回滚

### 6.1 回滚机制

#### 6.1.1 回滚触发条件

| 类别 | 触发条件 |
| --- | --- |
| 版本质量 | 新版本崩溃率**高于**上一版本（不设绝对阈值，采用相对比较，避免受用户机器差异干扰） |
| 版本质量 | 客户端启动成功率下降（主进程连续 3 次启动失败的设备数上升） |
| 性能 | 冷启动到可交互 P95 &gt; 3 秒，或空闲内存 &gt; 300MB（N1 基线不达标） |
| 性能 | P99 端到端响应 &gt; 1000ms 持续 5 分钟（AL-06） |
| 关键告警 | 灰度批次内出现任一 P0 告警（AL-01 / AL-02 / AL-03） |
| 关键告警 | 灰度批次内出现两条及以上 P1 告警且指向同一根因 |
| 数据完整性 | 审计哈希链校验失败（AL-11） |
| 分发链路 | 差分更新下载成功率低于 90% 持续 1 小时（AL-15） |

#### 6.1.2 回滚决策人

| 场景 | 决策人 |
| --- | --- |
| 灰度批次内的清单撤回（停止放量） | `@研发团队-平台与安全组` 可独立决定，无需跨团队审批（速度优先） |
| 正式通道全量后的版本回滚 | 至少 1 名 Owner 审批；涉及数据兼容的需追加 `@研发团队-Agent 组` |
| 用户侧的单机回退（用户自行回退到上一版本） | **用户本人**（客户端提供「回退到上一版本」入口） |
| 云端侧的会话级处置 | 用户本人；云端不做实例回滚，改为重新投射（IC-09 方案 A） |

#### 6.1.3 回滚执行 SOP

| 对象 | 回滚方式 | 预计耗时 | 有损风险 / 数据丢失 |
| --- | --- | --- | --- |
| 客户端版本（灰度清单） | 更新元数据端点（META）撤回新版本清单 → 客户端下次检查更新时收到上一版本清单 | ≤ 5 min（取决于客户端检查周期） | 无；已升级的客户端需等待下一次更新检查 |
| 客户端版本（用户单机回退） | 客户端内「回退到上一版本」入口 → 下载上一版本全量包 → 覆盖安装 | 取决于用户网络与包体积 | **无数据丢失**（数据与程序分离，数据目录不受安装影响） |
| 配置（L2） | 配置中心保留历史版本（每次变更留存），一键回退到上一版本 | &lt; 1 min | 无；配置变更必须幂等，回退亦幂等 |
| 数据（SQLite 事件库） | 从全量快照还原（§6.2 RB-03） | ≤ 30 min（整机口径） | **有**：RPO ≤ 24 小时（整机口径）；进程崩溃口径 RPO ≤ 200 毫秒 |
| 数据库结构变更（DDL） | **DDL 变更必须可回滚**；不可回滚的 DDL（如 DROP COLUMN）**禁止与代码同发布**，须前置单独变更并留回滚脚本 | &lt; 30 min | 有；故前置变更是硬要求 |
| 云端会话 | **不适用（无回滚概念）**：失败时销毁并重新投射一次 | 待 Q4 补齐后定义 | 云端无持久状态，无数据丢失；本地主副本不受影响 |
| 云端镜像版本 | 投射时指定上一版本镜像（新旧镜像并存） | 取决于镜像拉取耗时 | 无 |

**桌面端回滚的两条特有约束**：

1. **程序与数据分离是回滚可行的前提**：数据目录（R-S-001）与安装目录分离，因此卸载重装或版本回退**不影响用户数据**。任何把数据写进安装目录的设计都会破坏这一前提。
2. **不可回滚 DDL 必须前置变更**：桌面端的 DDL 变更随客户端升级下发，一旦用户已升级就无法「回收安装包」，因此不可回滚的 DDL 必须与代码发布解耦，单独前置一个版本执行。

#### 6.2.2 Runbook 编写规范

每条 Runbook 按以下结构编写：

- **症状**：触发该 Runbook 的可观测特征（大盘指标 / 告警内容 / 用户反馈）
- **诊断（按顺序执行）**：定位根因的诊断步骤，明确使用的可观测工具与查询路径
- **缓解**：分场景的处置动作（与 §6.1 回滚、降级、限流、切换等机制衔接）

#### 6.2.3 RB-01：事件库不可写或检查点写入失败

- **症状**：
  - 告警 AL-01 触发（事件库连续写入失败 3 次 / 30 秒，或 SQLite 不可写）；
  - 或告警 AL-05 触发（检查点写入失败）；
  - 用户侧表现为执行流不再更新、任务停止推进、UI 出现「事件库不可写」提示。
- **诊断（按顺序执行）**：
  1. 打开内置「中间件与存储大盘」，查看 SQLite 写 QPS、慢查询数、WAL 大小、库文件体积四项；
  2. 检查库文件体积是否逼近 8GB 归档阈值——若逼近，根因为容量而非写入通道；
  3. 检查工作区所在磁盘使用率（「容量与资源大盘」），判断是否进入 95% 红线水位；
  4. 检查 `t_event` 的序列缺口数，确认是否有已写入但序列断裂的情况；
  5. 查看本地 JSONL 日志（R-O-002）中 `module = M2` 的 ERROR 条目，取 `traceId` 后到「本地导出 OTLP JSON」中检索完整调用链。
- **缓解**：
  - 场景 A（容量逼近阈值）→ 执行强制归档，释放热数据至 8GB 以下；归档为离线操作，可后台执行；
  - 场景 B（磁盘进入红线水位）→ 提示用户清理磁盘；清理前不接受新任务（与 §3.5.3 限流红线一致）；
  - 场景 C（写入通道本身故障，如文件权限被改）→ 按《系统设计》§2.5.2 的 BD-01 处理为 fail-stop，**不返回降级数据、不写脏数据**；
  - 场景 D（进程 P-04 崩溃导致）→ P-01 监护重启 P-04，从最近检查点续跑。
- **升级**：
  - 30 分钟内未恢复 → 引导用户导出诊断包（含日志、指标摘要与最近 1000 条审计链校验结果）并提交；
  - 出现数据一致性疑虑时 → 优先执行 RB-03 从全量快照还原，**优先保证数据正确而非任务继续**；
  - 对外通告：本系统无对外服务，无需对外通告；仅在版本发布说明中记录已知问题。

#### 6.2.4 RB-02：客户端启动失败或 Agent 主循环崩溃

- **症状**：
  - 告警 AL-02（主进程连续 3 次启动失败）或 AL-03（P-03 五分钟内崩溃 ≥ 3 次）；
  - 用户侧表现为双击图标无响应、启动后立即退出、或主控台卡在加载态。
- **诊断（按顺序执行）**：
  1. 检查是否为三平台共性问题还是单平台问题——查看崩溃上报（若用户已开启）中的 OS 版本与架构分布；
  2. 检查 `vendor/vscodium` 是否完整（首启即崩的常见根因是 asar unpack 规则遗漏导致 VSCodium 资源解压失败）；
  3. 检查原生模块 ABI：查看 `build-info.json` 中的 `electron-version` 与运行时 `process.versions.modules` 是否一致；
  4. 若为 P-03 崩溃，检查其内存占用曲线——判断是否因长程任务上下文膨胀触发内存软限额；
  5. 查看本地日志中 P-01 与 P-03 的 ERROR 条目及其 `traceId`。
- **缓解**：
  - 场景 A（原生模块 ABI 不一致）→ 回滚到上一版本（RB-08），并在流水线阶段 1 修复 ABI 断言；
  - 场景 B（asar unpack 遗漏）→ 回滚到上一版本，并修正 unpack 规则后重新构建；
  - 场景 C（P-03 内存超限）→ 本应为自动行为（触发上下文压缩）；若未触发，降低并行度至 1 并观察；
  - 场景 D（主进程崩溃且无法自恢复）→ 引导用户执行「清除本地数据并重装」（需二次确认，此操作会清除本机数据）。
- **升级**：
  - 影响范围涉及多个用户设备时 → 立即停止当前灰度批次（RB-08）；
  - 崩溃率高于上一版本 → 全量回滚；
  - 需用户配合时 → 引导开启崩溃上报（默认关闭）后再复现一次。

#### 6.2.5 RB-03：整机或磁盘故障后的数据恢复

- **症状**：
  - 用户更换设备、重装系统或磁盘损坏后重新安装客户端；
  - 或本地磁盘进入红线水位 → 由 AL-09 升级而来。
- **诊断（按顺序执行）**：
  1. 确认备份目录（R-S-002）是否可用——若与生产库在同一磁盘且磁盘已损，则备份同时丢失；
  2. 列出可用的全量快照（保留 30 天，每日 1 份，滚动覆盖），选取最近一份；
  3. 检查快照完整性（SQLite 快照由 `VACUUM INTO` 产出，可直接打开验证）；
  4. 若有外部备份路径（用户自行指定），优先从外部路径恢复。
- **缓解**：
  - 场景 A（本機备份可用）→ 还原最近全量快照到数据目录 → 启动客户端 → 校验审计哈希链（每次启动自动校验最近 1000 条）；
  - 场景 B（本機备份不可用）→ 若有增量导出（保留 180 天），按运行维度逐个导入事件与检查点；
  - 场景 C（全部不可用）→ 客户端以空库启动；**用户在用户工作区的代码不受影响**（工作区在用户自有文件系统内，由用户自行用 Git 版本管理）。
- **升级**：
  - 恢复后必须执行一次「从检查点续跑」验证，确认事件流与检查点自洽；
  - 恢复后必须执行审计哈希链完整校验；
  - 该 Runbook 是「每季度 1 次恢复演练」的必演项。

#### 6.2.6 RB-04：分发与更新链路故障

- **症状**：
  - 告警 AL-15（更新检查连续失败 5 次，或差分下载成功率低于 90% 持续 1 小时）；
  - 告警 AL-16（流水线阶段失败，尤其阶段 5 签名 / 公证失败）；
  - 用户侧表现为「检查更新」无响应、更新下载中断、或 macOS 提示「已损坏，无法打开」。
- **诊断（按顺序执行）**：
  1. 用浏览器直接访问更新元数据端点，确认版本清单可读（若不可读，根因在分发链路）；
  2. 检查流水线阶段 5 的日志，定位是构建失败、签名失败还是公证失败；
  3. 若为 macOS「已损坏，无法打开」→ 根因几乎必为公证缺失或 stapling 失败，检查阶段 5 的 notarize 步骤；
  4. 若为 Windows SmartScreen 拦截 → 根因为签名证书声誉未建立，确认证书类型（OV / EV）；
  5. 检查 R-S-004 分发桶的可用性与 CDN 命中率。
- **缓解**：
  - 场景 A（分发链路不可用）→ 临时切到对象存储公网端点直连（绕过 CDN）；
  - 场景 B（差分下载失败）→ 客户端自动回退全量包下载；若全量包也失败，暂停发放更新清单；
  - 场景 C（公证失败）→ **不得产出无公证的 macOS 制品**；修复后重新执行阶段 5；
  - 场景 D（签名失败）→ 同上，不得产出无签名制品；
  - 场景 E（新版本有缺陷）→ 执行 RB-08 撤回清单。
- **升级**：
  - 影响全部用户的分发中断持续 1 小时 → 提升为 P1 并通知全部 Owner；
  - 证书即将到期 → 触发 §4.5.2 的证书轮换流程（新旧并存 ≥ 一个版本周期）。

#### 6.2.7 RB-05：云端投射 / 取回失败与孤儿实例残留

&gt; 本 Runbook 在 Q4 补齐后才生效；在 Q4 补齐前，云端入口置灰（BD-12），不会出现该故障。

- **症状**：
  - 告警 AL-14（云端投射或取回连续失败 3 次）；
  - 告警 AL-17（云端孤儿实例连续 2 次夜巡未成功回收）；
  - 用户侧表现为云端工作区创建失败、云端沙箱会话启动失败。
- **诊断（按顺序执行）**：
  1. 确认用户云账号凭据有效（设置与凭据中心的连通性自检）；
  2. 确认用户账号配额是否触顶（配额属用户自有账号，本系统只能读取其暴露的配额信息）；
  3. 检查 `t_workspace_projection` 台账中最近投射记录的状态位；
  4. 若为孤儿实例残留 → 检查夜巡任务是否执行、回收脚本是否有权限（CAM 策略，R-Sec-004）；
  5. 若为取回失败 → 检查 E-12r（用户自有 Git 远端）的可达性与凭据引用是否有效。
- **缓解**：
  - 场景 A（投射失败）→ **不修复实例，直接重新投射一次**（IC-09 方案 A）；
  - 场景 B（孤儿实例）→ 手动触发夜巡回收；回收必须一并释放临时存储（R-S-006）与反代路由；
  - 场景 C（配额触顶）→ 提示用户；本系统无权调整用户配额；
  - 场景 D（云端能力整体不可用）→ 云端入口置灰（BD-12），**本地链路照常**，用户的工作不中断。
- **升级**：
  - 连续 3 次重新投射仍失败 → 提示用户检查自有云账号状态，并建议其联系腾讯云支持；
  - 本系统侧不做云端设备的运维介入（资源不归本系统所有）。

#### 6.2.8 RB-06：LLM 供应商故障

- **症状**：告警 AL-04（LLM 调用错误率 &gt; 10% 持续 5 分钟，或单一供应商连续 3 次 429 / 5xx）。
- **诊断（按顺序执行）**：
  1. 在「运行健康大盘」查看 LLM 调用成功率与首字延迟，区分是超时、限流还是鉴权失败；
  2. 检查凭据轮换提示（AL-12），排除 Key 失效；
  3. 检查该供应商端点是否登记在出网白名单内（E-01 / E-02）；
  4. 若为 429 → 判断是否触及本系统侧限流（60 次/分钟 / 供应商）还是供应商侧限流。
- **缓解**：
  - 场景 A（供应商侧限流或 5xx）→ 指数退避重试；持续失败则切换供应商（双协议两套凭据互不影响）；
  - 场景 B（本系统侧限流触顶）→ 排队，按 IC-12 并行上限与五维限流处理；
  - 场景 C（凭据失效）→ 提示用户轮换凭据（AL-12）；
  - 场景 D（单供应商完全不可用）→ 切换另一协议供应商；若两家均不可用，任务暂停并保留检查点，可续跑。
- **升级**：
  - LLM 费用与用量由用户自付，本系统不做成本侧干预，只提供用量归集与花费展示；
  - 凭据轮换由用户自助完成（本系统不代持 Key）。

#### 6.2.9 RB-07：审计哈希链断链

- **症状**：告警 AL-11（任一条审计记录断链）；客户端启动时自动校验最近 1000 条链的完整性。
- **诊断（按顺序执行）**：
  1. 定位断链的 `seq` 位置（审计表内 `prev_hash` / `self_hash` 串联）；
  2. 检查该位置前后是否有归档操作（归档只做冷存，**不删除**审计记录，若发生删除即为缺陷）；
  3. 检查是否为外部直接改库（本系统禁止对 `t_audit_event` 做软删与物理删）；
  4. 交叉核对同一 `traceId` 下的事件流记录是否存在。
- **缓解**：
  - 场景 A（归档操作误删）→ 从归档目录（R-S-003）还原该段记录；
  - 场景 B（外部篡改）→ 保留现场、导出诊断包，并在 UI 明示审计完整性受损；**不做静默修复**；
  - 场景 C（写入中断导致的链断裂）→ 从最近全量快照还原审计链。
- **升级**：
  - 审计完整性受损属高严重度问题（直接冲击 N3 的 100% 留痕承诺），必须记录到版本发布说明；
  - 若疑为社会工程或本地恶意软件所致 → 提示用户做全机安全检查（本系统不做杀毒）。

#### 6.2.10 RB-08：版本发布回滚

- **症状**：
  - 灰度批次内出现 P0 告警，或崩溃率高于上一版本，或冷启动 P95 / 空闲内存基线不达标；
  - 或分发链路异常（AL-15）导致大面积更新失败。
- **诊断（按顺序执行）**：
  1. 在「发版与分发大盘」确认受影响范围（按版本与通道统计）；
  2. 对比新旧版本的崩溃率、启动成功率、冷启动 P95、空闲内存四项；
  3. 定位根因所属模块（P-01 ~ P-07 中的哪个进程、M1 ~ M15 中的哪个模块）；
  4. 判断是否需要数据回滚（若新版本写入了不兼容的数据结构）。
- **缓解**：
  - 场景 A（灰度批次内）→ 立即撤回新版本清单（≤ 5 min），停止放量；
  - 场景 B（已全量）→ 撤回清单 + 发布上一版本为「推荐版本」，引导用户回退；
  - 场景 C（需要数据回滚）→ 先执行数据回滚（从快照还原），再执行版本回滚；**顺序不可颠倒**；
  - 场景 D（分发链路问题而非版本问题）→ 按 RB-04 处理，不回滚版本。
- **升级**：
  - 回滚后必须在流水线阶段 7 复跑四项发版必测，定位被门禁漏过的根因；
  - 若根因是门禁本身缺失 → 补充门禁项后再发布（形成闭环）。

#### 8.2.2 月度成本估算方法

**月度总成本公式（云端与分发部分）**

```
月度总成本 = Σ(分项 i 的 单价 × 分项 i 的 月度计量值)

其中各分项的月度计量值口径：
  云端计算月度计量值 = 月度投射次数 × 单次会话时长 × (1 + 预热池冗余系数)
  云端存储月度计量值 = 镜像版本数 × 单镜像体积 + 预览资源日增 × 保留天数
  云端网络月度计量值 = 月度投射数据量 + 月度预览访问流量
  分发链路月度计量值 = 月度下载次数 × 平均下载体积(差分后) + 月度回源流量
  CI 执行器月度计量值 = 月度流水线次数 × 单次流水线耗时 × 三平台并发数
```

**Q4 补齐前的状态声明**：上述公式中，**全部「单价」与全部云端侧「月度计量值」在 Q4 补齐前均为空值（null）**。因此月度总成本**当前不可计算**，本文档不给出任何区间估算。这是刻意的设计——给出区间估算等于变相给出成本型承诺，直接违反 C4。

#### 8.2.3 年度成本估算方法

**年度总成本公式**

```
年度总成本 = 月度总成本 × 12 + 年度固定项

年度固定项 = 代码签名证书年费 + Apple Developer Program 年费
           + 泛域名证书年费(ACME 为 0 元) + CI 执行器年费(若自建为硬件摊销)
```

**Q4 补齐前的状态声明**：与月度同理，年度总成本在 Q4 补齐前不可计算。本文档只固化**公式与分项清单**，补齐输入后即可直接求值，**不需要重新设计成本模型**。

#### 8.2.4 成本控制的部署侧手段（不依赖数值即可落地）

| 手段 | 作用机制 | 量化收益口径 |
| --- | --- | --- |
| 差分更新（blockmap） | 小版本只下载变更块，而非全量包 | 更新下载流量 = 全量包体积 × 差分率（差分率 &lt; 1，具体值取决于版本间差异） |

### A.1 U-05（腾讯云 CVM 是否透传 /dev/kvm）的实测方案

&gt; U-05 决定云端沙箱的隔离原语：若 CVM 透传 `/dev/kvm` 且 CPU 具备虚拟化扩展，则可走 **Firecracker microVM**（每沙箱独立内核，硬件级隔离）；若不透传，则只能退回**容器**（共享内核，隔离弱于 microVM）。该降级必须显式承认（C5）。

#### A.1.1 实测命令（四条，在候选实例上依次执行）

| 序号 | 命令 | 判读 |
| --- | --- | --- |
| 1 | `ls -l /dev/kvm` | 输出中存在 `/dev/kvm` 设备节点为**必要条件**；若报 `No such file or directory`，则直接判定为不支持 |
| 2 | `systemd-detect-virt` | 确认虚拟化类型；输出 `none` 表示宿主为裸金属或支持嵌套虚拟化的实例，输出 `kvm` 等表示本身已是虚拟机（需进一步看嵌套支持） |
| 3 | `grep -cE 'vmx\|svm' /proc/cpuinfo` | 统计 CPU 虚拟化标志数（Intel VT-x 为 `vmx`，AMD-V 为 `svm`）；**结果需大于 0** |
| 4 | `[ -r /dev/kvm ] && [ -w /dev/kvm ] && echo RW_OK` | 验证当前用户对 `/dev/kvm` 具备**读写权限**（仅有设备节点但无权限同样不可用） |

&gt; 补充一条功能性验证（在完成上述四条后执行）：在实例上实际启动一个 Firecracker microVM 并确认其可进入命令行，这是唯一能排除「节点存在但不可用」的终检。

#### A.1.2 判定标准

| 判定结果 | 条件 | 隔离原语 |
| --- | --- | --- |
| 支持 | 四条命令全部满足，且功能性验证通过 | **Firecracker microVM**（每沙箱独立内核，硬件级隔离） |
| 不支持 | 第 1 条或第 3 条不满足，或第 4 条无权限 | **容器**（共享内核，隔离弱于 microVM）→ 必须在 UI 与对外文档中原样展示 C5 降级声明 |
| 不确定 | 四条满足但功能性验证失败 | 暂按容器处理并显式标注「隔离原语未能确认」，**不得声称 microVM** |

| 退路 | 内容 | 代价 |
